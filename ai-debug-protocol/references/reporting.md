# Reporting & Stop Protocol — 报告、访谈、停机

## 调试报告模板（每份交付必带）

```markdown
# 调试报告
## 证据（Seen）
- [命令] → [输出摘录]（附文件路径/截图名）

## 假设（标注 Remembered / Guessed）
- H1: …（依据: …）

## 实验（一假设一实验）
- E1: 命令 → 观察 → 结论（支持/反驳 H1）

## 结论或卡点
- 根因一句话：… / 卡在：…（需要用户提供/执行什么，精确到命令或文件）

## 判据
- done 检查：[命令] → [结果]
- 不可动项：[status]

## 未验证（每条带验证命令）
- [item] → [command]

## 信心度：N/5
- 为什么不是 5；哪一类证据能把它推到 4-5
```

规格：证据不带形容词；每个 Guessed 假设必须配一条"转 Seen"的命令；结论一句话（说不出根因就不许写结论段）。

## Interview-Until-Spec（需求模糊时的正确停顿）

用户症状模糊（"不好用"/"有问题"）→ 不要开始猜，问出可判定 spec 为止：
1. 你看到的现象（可截图/可复述的哪一句）
2. 期望的行为（done 判据的原料）
3. 最近改动（ bisect 的起点）
4. 你能提供的访问（日志/进程/仓库路径）
拿到能写"复现锚点 + done 判据"的信息才动手；拿不到 → 报告"信息不足，需要 X"，这是合法交付。

## 显式停机条件（停下来上报，不变通）

| 信号 | 停机动作 |
|---|---|
| 缺信息/缺凭据/缺权限 | 要精确的东西（日志某段/一个文件名/一次授权），不给笼统"更多细节" |
| 约束冲突（要动禁区/破坏不可动判据） | 列出冲突，给选项，等指令 |
| 同一形状的假设连败两次 | 系统模型错了——回到观测，别硬打补丁 |
| 破坏性操作无验证过的回滚 | 先建回滚点（快照/tag/dump）再动，或不做 |
| 观测缺失但结论要下 | 标 Guessed，写进未验证清单，不混进结论 |

变通路径是禁区：Codex 被 sudo 挡住后自己找变通办法 = 典型翻车。阻塞是一等公民，上报不是失败。

## 破坏性变更解锁清单（8 项全勾才动 schema/数据/生产配置）

GREEN-2 停机案例的落地清单，"急着上线"不抵扣任何一项：

```markdown
[ ] 全量备份已 restore 验证过（不是"备份做了"，是"拿备份重建过"）
[ ] binlog 位点/时间点恢复路径明确
[ ] 回滚脚本已同批提交且演练过一次
[ ] expand→migrate→contract 三阶段（不原地改）
[ ] 回填校验查询已写好（行数/抽检/一致性）
[ ] 灰度顺序（谁先走新结构）
[ ] 老客户端回归用例覆盖
[ ] 变更记录（什么时候/为什么/谁批的）
```

停机期间不等死：并行交付只读影响卡（SHOW CREATE TABLE、体量、索引、外键依赖、代码引用面），急着上线的人拿到的是可执行的影响面，不是干等。

## 无人值守时的五连问（派活方自检用）

1. 你知道"完成"长什么样吗（done 判据）？
2. 你能自己验证吗（可运行的检查）？
3. 允许碰什么（禁区清单）？
4. 什么情况必须叫停（停机条件）？
5. 结果交给谁验收（报告格式）？

——这五问也适用于你给别人派调试活前的自检。
